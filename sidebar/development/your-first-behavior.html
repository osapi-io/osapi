Your first behavior

In this tutorial, you build a behavior that reads and sets the message of the day of a host, /etc/motd. At the end, it has an API route, CLI commands, a docs page, telemetry, a setting and tests at each layer. You write the types, the provider and some examples. osapi builds the rest from the definition, the tests too.

Building a behavior is the reference for everything used here. This page is the walk through it.

What we will build​

A motd behavior with two methods:

MethodDoesServed at
getreads the message of the dayGET /api/node/{hostname}/motd
updatereplaces itPUT /api/node/{hostname}/motd

and one setting, behaviors.motd.path, the file it manages.

Before we start​

You need a checkout of osapi with its tools, as Contributing tells. It must build and pass:

just deps
just test

With an agent, the full tutorial is one request. The build-a-behavior skill in this repository has these steps, and each coding agent in a checkout loads it:

Build a motd behavior that reads and sets /etc/motd.

The agent runs the commands below and checks its own work with the same tests. Reading on is how you review what it wrote.

Check what exists​

Before you write anything, ask the binary what it has:

go run . behavior list

The list comes from the registry of the binary, so it is always current. If a behavior similar to motd is there, extend it. Do not add a second one.

Create it​

go run . behavior create --name motd --description "The message shown at login"

That writes internal/behaviors/motd/ and registers it with one import in internal/behaviors/all. Nothing else outside the directory changes, now or later.

internal/behaviors/motd/
  behavior.go    behavior_public_test.go   the definition; validates it and runs the examples
  methods.go     methods_public_test.go    get and update, on a mocked provider
  provider.go                              the Provider interface
  debian.go      debian_public_test.go     the provider on Debian: keeps a value in a file
  settings.go                              behaviors.motd.path and its default
  types.go                                 the input and output types
  mocks/                                   the provider's double, generated

It is already a working behavior: a value kept in a file. Generate the mock and the gen/ directory, and notice that it passes before we change anything:

go generate ./internal/behaviors/motd/mocks ./internal/behaviors/all
go run . behavior validate
just test

Now gen/ has a handler for each method (api_get.go and api_update.go), the route table in api.go, the commands in cli.go, the spec in api.yaml, and a test next to each Go file.

The rest of the tutorial turns that value into the message of the day.

Point the setting at /etc/motd​

Settings are the fixed configuration of the agent. Each one gets a default, an environment variable and an agent start flag:

internal/behaviors/motd/settings.go
const defaultPath = "/etc/motd"

type Settings struct {
    Path string `mapstructure:"path" doc:"The file motd manages." validate:"required,startswith=/"`
}

var defaults = Settings{Path: defaultPath}

A value that changes with each call never goes here. It is the input of the method.

The types​

The tags of the input and output types hold all of the contract. Each input field becomes a flag and a request field. Each output field becomes a column and a JSON field. The value of the scaffold already fits, so you only describe it:

internal/behaviors/motd/types.go
type UpdateInput struct {
    Value string `json:"value" validate:"required" doc:"The message, shown at login"`
}

type Entry struct {
    Value string `json:"value" doc:"The message"`
}

type Result struct {
    Changed bool `json:"changed" doc:"Whether the host changed"`
}

Notice changed on the write's output. Every write reports whether it changed the host, which is what makes running it twice safe to reason about.

The provider​

The provider does the work. The scaffold's Debian provider already reads and writes the file in the setting, through the agent's filesystem:

internal/behaviors/motd/debian.go
func newDebian(h host.Host) (Provider, error) {
    return &debian{fs: h.FS, path: host.Settings[Settings](h).Path}, nil
}

func (d *debian) Set(_ context.Context, value string) (bool, error) {
    if current, err := d.fs.ReadFile(d.path); err == nil && string(current) == value {
        return false, nil
    }
    _ = d.fs.MkdirAll(filepath.Dir(d.path), 0o755)

    return true, d.fs.WriteFile(d.path, []byte(value), 0o644)
}

Notice that Set compares before it writes: setting the message it already has changes nothing and says so. host.Host is what the agent hands every provider: the platform, the filesystem, a command runner, the file state store and the behavior's settings.

The definition says which platforms have a provider. On any other, the methods report skipped rather than fail:

behavior.Platform("debian", newDebian),

A provider declares each program that it runs. Use behavior.Sudo("program") for a program that it runs with sudo. The preflight of the agent checks it. Use behavior.Runs("program") for a program that it runs without sudo. The agent gives a warning when it is missing. The tests fail when a program runs without its declaration.

The examples​

The examples are what the docs pages show, and they are also the provider's tests. Each one says what the host looks like first and what the call changes:

internal/behaviors/motd/behavior.go
behavior.Read("get", Get).
    Describe("Get the message of the day").
    Example("Before anything is set", GetInput{}, Entry{}).
    Example("The message", GetInput{}, Entry{Value: "Authorized use only."},
        behavior.After(UpdateInput{Value: "Authorized use only."}),
    ),
behavior.Write("update", Update).
    Describe("Replace the message of the day").
    Example("A new message", UpdateInput{Value: "Back at 5pm."}, Result{Changed: true},
        behavior.Wrote(defaultPath, "Back at 5pm."),
    ),

After runs a different method first, here update, so that get has something to read. Wrote says that the file has exactly that text after the call. A provider that runs commands names them with Ran. A provider that reads the output of a command gives it with Prints. Declare what a method refuses in the same way, with .Fails("No message", UpdateInput{}, "value must not be empty"), when the provider checks for it.

Generate and confirm​

go generate ./internal/behaviors/all
go run . behavior validate
go run . behavior get --name motd
go run . config get --key behaviors.motd.path

validate checks the definition against every rule the platform relies on. get shows the routes, permissions, platforms, types, the setting and the telemetry, exactly as the binary registered them. config get shows the setting's default, its environment variable OSAPI_BEHAVIORS_MOTD_PATH and its agent start flag --motd-path.

The tests we did not write​

just test

You wrote no test. The tests of the scaffold cover its own code. methods_public_test.go calls each method on a mock provider. debian_public_test.go runs the provider on an in-memory filesystem. behavior_public_test.go validates the definition. It has one line, behaviortest.Run(s.T(), motd.Behavior), that runs the examples and refusals through the methods and the provider. osapi generates the rest from the definition:

WhatChecks
The provider, on DebianEach example on a fake host gives its output and its effects; update run twice reports changed: false; a failing call never panics
The APIgen/api_get_public_test.go and gen/api_update_public_test.go: each example through the real handler, the response matching the spec, broadcast, 401, 403, 500, and a missing value is a 400
The CLIgen/cli_public_test.go: each example's flags, given to the generated command, send the example's input
The live servergo test -tags integration runs get against a real agent, and the writes too with OSAPI_INTEGRATION_WRITE_BEHAVIORS=1; CI's Integration step runs them as root, with OSAPI_INTEGRATION_WRITE_BEHAVIORS=1, on its throwaway Linux runner, each from its item deleted; a behavior with no delete gets its item back afterwards, through get and update. A write example sets its starting state with After, which a live host can run

To see them for motd alone:

go test ./internal/behaviors/motd/... -v

A provider test of our own is only for what an example cannot show, such as a parser's edge cases.

Run it​

Start osapi with a token, as Getting Started shows, then:

osapi client node motd update --value "Back at 5pm."
osapi client node motd get
osapi client node motd update --value "Back at 5pm."

Notice the second update reports no change: the host already has that message.

What we built​

One directory, one import line, and a behavior with:

  • GET and PUT routes, permission checks granted to the built-in roles, broadcast targeting and the {job_id, results[]} envelope
  • osapi client node motd get and update, with typed flags
  • an OpenAPI spec, under API
  • a docs page under Behaviors, with each example rendered as the CLI prints it and what it changes on the host
  • a provider the agent builds on Debian, skipped elsewhere
  • a span and three metrics on every call
  • a setting with a default, an environment variable, a flag and validation
  • provider, API, CLI and integration tests, from the examples.
