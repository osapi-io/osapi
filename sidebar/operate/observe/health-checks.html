Health checks

osapi has health endpoints for load balancers, monitoring systems and operations tools. These endpoints report if the controller runs, if it is ready for traffic, and the status of its dependencies. The three components (controller, agent, NATS server) write to one shared registry. Thus an operator can see the health of all of the deployment from one endpoint.

Endpoints​

EndpointAuth RequiredDescription
/api/healthNoLiveness probe: does the process run?
/api/health/readyNoReadiness probe: is it ready for traffic?
/api/health/statusYesDetailed status with component health metrics

Liveness (/api/health)​

Always returns 200 OK if the process runs. Use it in container orchestrators, for example in a Kubernetes liveness probe, to find processes that do not respond.

Readiness (/api/health/ready)​

Checks connectivity to NATS and KV stores. Returns 200 OK when the controller can process requests, or 503 Service Unavailable when dependencies are down. Use this for load balancer health checks to avoid routing traffic to an unready instance.

Status (/api/health/status)​

Returns the health of each component, with system metrics (uptime, goroutine count, memory use). It needs authentication with the health:read permission. Use it for dashboards and monitoring. It answers 200 when a component is not healthy, with the overall status degraded: the request worked. Use /api/health/ready to route traffic.

Component registry​

The three components write a heartbeat to a shared registry KV bucket at a regular interval. Each heartbeat writes a JSON record. The key is the component type and the hostname, for example agents.web-01, controller.api-server or nats.nats-server. The records have process metrics from the time of the heartbeat:

MetricDescription
CPU percentProcess CPU utilisation at sample time
RSS bytesResident set size (physical memory used)
GoroutinesNumber of active goroutines

The /api/health/status response has a components table that puts these heartbeat records together. If the registry key of a component expired (the TTL ended without a new heartbeat), osapi reports the component as unreachable.

Each row has the build version of the component's binary, so a mixed fleet shows which hosts run an older build. Example registry output:

Components (3):
  TYPE          HOSTNAME     STATUS  CONDITIONS  AGE    CPU %  MEM       VERSION  ADDRESS
  controller    api-server   Ready   -           7h 6m  2.10   128.0 MB  v0.2.1
  ├─ api                     ok      -                                          http://0.0.0.0:8080
  └─ heartbeat               ok      -
  nats          nats-server  Ready   -           7h 6m  0.30   64.0 MB   v0.2.1
  └─ server                  ok      -                                          nats://localhost:4222
  agent         web-01       Ready   -           7h 6m  1.20   96.0 MB   v0.2.1
  └─ heartbeat               ok      -

Sub-Component health​

Each component publishes the status of its internal services with its heartbeat. The /api/health/status endpoint puts these parts together from the registry. Thus an operator can see the health of each internal service on all hosts, also in a deployment with many nodes.

Each component reports only its own sub-components. The answer lists them under the component's registry entry, as components, sorted by name. The tables name each one with its type, as the heartbeat does:

ComponentSub-Components
controllercontroller.api, controller.heartbeat, controller.metrics, controller.notifier, controller.tracing
agentagent.heartbeat, agent.metrics
natsnats.server, nats.heartbeat, nats.metrics

Sub-components report a status (ok, disabled, or error) and an optional network address and URL. osapi client health status prints each one under its component, as a tree. The controller also checks its connection to NATS and to KV for each answer. These are in checks, each with its name (nats or kv), its status and, when it failed, its error.

Metrics server health probes​

In addition to the controller's REST health endpoints, each component's metrics server also exposes lightweight probes on its own port. These are separate from the REST API health checks and require no authentication.

EndpointPort (default)Description
/health9090 / 9091 / 9092Liveness. Always returns 200
/health/ready9090 / 9091 / 9092Readiness. 200 when ready, 503 when not

Use these probes to monitor each component without the controller API. For example, a Kubernetes pod spec or an external load balancer can probe the metrics server of the agent or of NATS directly.

Refer to Metrics for probe details and a Kubernetes example.

Condition notifications​

When conditions fire, the notification system dispatches alerts. Refer to Notifications for the notification backends, configuration, and re-notification settings.

Configuration​

The health check endpoints (/api/health and /api/health/ready) need no authentication. They must work before clients have tokens. The /api/health/status endpoint needs a valid JWT with the health:read permission.

Health checks need only the standard server and authentication settings. Refer to Configuration for the full reference, CLI Reference for usage and examples, or the API Reference for the REST endpoints.
