Audit logging

OSAPI records a structured audit trail of every API request. Audit entries capture who made the request, what they did, and how long it took. This provides accountability and supports compliance requirements.

How it works​

A middleware in the API server records audit entries automatically. Each authenticated request makes an audit entry. osapi stores it in its own NATS JetStream stream. No application code needs to log audit events. The middleware does it.

Each audit entry contains:

FieldDescription
idUnique entry identifier (UUID)
timestampWhen the request was made
userIdentity from the JWT sub claim
rolesRoles from the JWT token
methodHTTP method (GET, POST, etc.)
pathRequest path (e.g., /node/hostname)
operation_idOpenAPI operation ID (if available)
source_ipClient IP address
response_codeHTTP response status code
duration_msRequest processing time in milliseconds
trace_idOpenTelemetry trace ID (when tracing is enabled)
job_idThe job the request created, when it created one
request_summaryWhat the request asked for, redacted (see below)
stepsThe step tree of the job, for each host
chainThe steps of each host on one line

What the request asked for​

The client that called command/shell on a host, without the command, does not tell what happened. Thus, for each method that changes something (POST, PUT, PATCH, DELETE), the entry records request_summary. It is the request body as JSON. osapi replaces the values of sensitive fields with [redacted].

  • Redacted fields. osapi finds them by name, at all levels, and upper case or lower case does not matter. Thus it also redacts a password in a list of users: password, password_hash, secret, token, private_key, key_data, stdin, content, authorization. It also redacts each input field of type secret.Value, by its name. A reference, secret://<vault>/<key>, stays, so the entry shows which secret a request used.
  • The list is a deny list, not an allow list. osapi records new fields by default. A summary with only the fields that somebody remembered does not help after an incident. A field with a secret has the type secret.Value, and a test fails a string input field with a name on the list.
  • A summary has a limit of 2 KB. When osapi cuts it, it adds …[truncated]. osapi does not read a body of more than 64 KB. The entry says so. It does not keep the upload.
  • A body that is not JSON. osapi records its content type and size. It does not store the body.
  • A read records no summary. A GET has nothing that osapi must keep.

job_id connects an entry to the status timeline of its job. Thus "who asked for this" and "what the agents did" are one trail, not two. A request that makes no job has no job_id.

The chain of the job​

steps and chain record the behavior chain of the job: the calls of other behaviors that the method made on each host. steps is the tree of each host. chain is the same tree on one line for each host, as osapi client job get prints it:

Chain:      web-01: managedfile update (changed)

The job client gives the steps to the entry when it collects the response of a host. The entry records the steps also when a step failed, and the job failed on the host. A broadcast records the steps of each host that answered before the request returned. A host that answers after the request returned, such as after a timeout, is not in the entry. Its steps are in the job. A method that calls no other behavior has no steps and no chain.

The entry keeps the steps for the time that it keeps the entry. Thus the chain of an entry stays after the job expires from the job bucket.

Changes that do not go through the API​

Some changes do not go through the API, and the log has them too. Such an entry has an actor, the kind of who made the change, an action and a target. Its user is the name of the actor:

ActorUserActionTarget
systemauto_admitagent.admitthe machine ID
systemdelete_afteragent.deletethe machine ID
join-tokenthe token's IDagent.join (200, or 403 when refused)the machine ID
localthe user of the operating system of a commandjointoken.create, jointoken.revoke, token.generate, vaultkey.create, vaultkey.rotatethe token's ID, the token's subject, or the vault

A local command connects to NATS as the controller does, and writes its entry to the audit stream. An entry never has the token or a secret: only its ID. An entry of a request through the API has no actor.

osapi nats key create, nats auth ... create and nats setup write no entry: they run before the NATS server or its audit stream exists, or as a user that cannot write to it.

Viewing audit logs​

Query audit entries through the API or CLI. You can list recent entries (paginated), get a specific entry by ID, or export all entries. Refer to CLI Reference for usage and examples, or the API Reference for the REST endpoints.

Export​

Export gets all audit entries in one response, with no pages. Use it to keep entries for a long time. The audit entries in the NATS stream have a max_age that you can set (30 days by default). An export keeps them before they expire.

Without --json, the command shows the entries as a table. To keep them, send the JSON to a file:

osapi client audit export --json > audit.json

# Count the entries
jq '.items | length' audit.json

# Find the entries of a user
jq '.items[] | select(.user == "ops@example.com")' audit.json

# Write one entry on each line (JSONL)
jq -c '.items[]' audit.json > audit.jsonl

Retention​

osapi stores audit entries in a NATS JetStream stream, with retention settings that you can set. When entries are older than max_age, or when the stream is at its size limit, NATS removes the oldest entries automatically. If you must keep entries for a long time, export them before they expire.

Configuration​

nats:
  audit:
    stream: 'AUDIT' # JetStream stream name
    subject: 'audit' # Base subject prefix
    max_age: '720h' # 30-day retention (default)
    max_bytes: 52428800 # 50 MiB max stream size
    storage: 'file' # "file" or "memory"
    replicas: 1 # Number of stream replicas

When stream is empty, the controller keeps no audit log. Each audit endpoint then answers 503, with a message that names nats.audit.stream.

When distributed tracing is enabled, each audit entry has a trace_id field. Use it to find the OpenTelemetry trace of the entry.

Refer to Configuration for the full reference.
